## 0. 한 줄 요약

**실행 중 요청과 새 요청이 앞으로 쓸 최고(peak) KV 를 트레이스의 알려진 출력 예산으로 일부(α) 예약하고, 풀을 넘길 요청은 입장을 늦춘다.**

## 2. 네 문장 (hint 1절, 실측값으로)

1. 부하 **q0.6 이상**에서 **maxITL p99(73 ms → q8 116.2 s)와 TTFT p99(70 ms → q8 78.2 s)**가 나빠지고, 서버에서 **token usage 1.00 과 #retracted_reqs(q0.6 1회 → q8 28회)**를 관측했다.
2. **KV 풀을 줄인(`--max-total-tokens 65536`) / chunked prefill 을 끈** 대조 실험은 **(실험 E2·E3 후 기입)**였으므로, 현재 가설은 **"KV 용량 대비 낙관적 admission"**이다.
3. 엔진의 **admission(`PrefillAdder.add_one_req`)** 결정만 바꾸면 **선점 횟수와 maxITL p99**가 줄어들 것이다.
4. 대신 **새로 도착한 요청의 TTFT 와 전체 완료 시간(E2E·wall)**이 나빠질 수 있고, 배치가 작아져 처리량이 줄 수 있다.

## 3. 설계 — 부분 peak-KV 예약

### 3.1 플래그

| 플래그 | 기본값 | 의미 |
|---|---|---|
| `--enable-peak-kv-reservation` | False | OFF 면 순정과 코드 경로가 같다 |
| `--peak-kv-reserve-ratio` | 1.0 | α. 남은 출력 예산 중 예약할 비율 (0~1) |

`server_args.py` 의 `retraction_policy` 필드([server_args.py:872](https://github.com/sgl-project/sglang/blob/v0.5.18/python/sglang/srt/server_args.py#L872))와 같은 패턴으로 `NS("schedule")` 필드 두 개를 추가하고, 스케줄러 쪽에서는 `get_schedule()` 로 읽는다(`NewTokenRatioTracker.from_config` 와 같은 방식).

### 3.2 동작

`PrefillAdder.add_one_req` 에서 기존 검사를 모두 통과한 뒤, admit 직전에 검사 하나를 **추가만** 한다. 기존 검사를 약하게 만들지 않으므로 OOM 위험은 늘지 않는다.

```python
# schedule_policy.py — add_one_req 안, 기존 예산 검사 통과 후
if sched.enable_peak_kv_reservation and not self._peak_kv_fits(req, cand_extend_input_len):
    return AddReqResult.NO_TOKEN

def _peak_kv_fits(self, req, extend_len) -> bool:
    if self.running_batch.is_empty() and not self.can_run_list:
        return True                                   # 불변식: 최소 1개는 받는다 (deadlock 방지)
    alpha = sched.peak_kv_reserve_ratio
    states = []                                       # (남은 토큰, 끝날 때 풀리는 토큰)
    for r in (*self.running_batch.reqs, *self.can_run_list, req):
        left = alpha * max(r.sampling_params.max_new_tokens - len(r.output_ids), 0)   # 4096 clip 없음
        freed = len(r.origin_input_ids) + len(r.output_ids) - len(r.prefix_indices)   # 공유 prefix 는 안 풀림
        states.append((left, freed))
    states.sort()
    free = self.cur_rem_tokens - self.ceil_paged_tokens(extend_len)   # available + evictable − 이번 라운드 사용분
    freed_so_far = 0
    for i, (left, freed) in enumerate(states):
        bs = len(states) - i
        if free + freed_so_far - left * bs <= IGNORE_EOS_RESERVE_TOKENS * bs:
            return False
        freed_so_far += freed
    return True
```

peak 계산은 기존 `add_one_req_ignore_eos` 의 루프([schedule_policy.py:1123-1131](https://github.com/sgl-project/sglang/blob/v0.5.18/python/sglang/srt/managers/schedule_policy.py#L1123))와 같은 식을 쓴다. 모든 요청이 한 step 에 1토큰씩 자란다고 보면, i 번째 요청이 끝나는 시점의 여유 = 지금 여유 + 먼저 끝난 요청이 푼 토큰 − 남은 bs 개 × left_i 이다.

α 의 의미:
- α = 1: 알려진 길이 전부 예약. `--disable-radix-cache` 오라클 경로와 선점 횟수가 비슷해야 한다(구현 검산용).
- α < 1: 일부만 예약. 선점을 일부 허용하는 대신 배치를 크게 유지한다.
- 이 조절 손잡이가 순정(`min(남은,4096) × 0.098`)과 오라클(α=1) 사이의 곡선을 만든다.

### 3.3 불변 조건 점검표 (hint 6절)

| 조건 | 대응 | 확인 방법 |
|---|---|---|
| 하나도 시작 못 하는 deadlock | 실행 중·이번 라운드 admit 이 모두 비면 검사를 건너뛴다 | 단일 요청 · 풀보다 큰 요청으로 테스트 |
| chunk continuation 차단 | `add_chunked_req` 경로에는 검사를 넣지 않는다 | W1 작은 trace 교차 재생 (W3 프롬프트 387토큰은 청킹 안 됨) |
| 재진입(선점) 요청의 영구 대기 | 대기열 순서는 유지되므로 앞 요청이 끝나면 들어간다. 선점 요청별 대기 시간 최댓값을 기록한다 | 서버 로그 재계산 줄 ↔ 클라 정지 시간 |
| 공유 prefix 이중 계산 | 끝날 때 풀리는 토큰에서 `prefix_indices`(캐시에서 받은 prefix) 길이를 뺀다 | 36토큰 시스템 prefix 가 있는 기본 trace |
| page 정렬 | `ceil_paged_tokens` 사용 (현재 page_size=1) | `--page-size 16` 스모크 1회 |
| 플래그 OFF = 순정 | 새 코드는 플래그 분기 안에만 둔다 | deterministic 모드 OFF 복사본 vs upstream verify |
| CPU 오버헤드 | 후보마다 O(n log n), n ≤ ~100 | 스케줄러 step 시간, 짧은 요청 TTFT |

## 6. 범위 밖 (이유와 함께 보고서 논의에 쓸 것)

- **FP8 KV (`--kv-cache-dtype fp8_e4m3`)**: 풀 2배로 λ_max 를 1.1~1.4 로 올릴 가능성이 가장 큰 레버지만, SGLang 기존 옵션이고 출력이 바뀐다. 천장을 올리는 것과 천장 근처에서 누가 기다리는지를 정하는 것은 다른 문제라는 논의에 쓴다.
- **선점 KV 를 host 로 swap**: 재계산 낭비가 0.2~8.4% 뿐이고 정지는 대기 때문이라 이득이 작다.
- **선점 요청 우선 재개**: 정지 원인(대기열 맨 뒤)에 직접 대응하지만 hint 방향이 아니고, 최적화는 하나만 한다.

These six deviations change how the plan's results should be read:

1. **α grid (P3).** The plan fixed α ∈ {0.25, 0.5, 1.0}. In P2, α = 0.5 never delayed an admission, so that run followed the flag-off trajectory. A smaller α only weakens the rejection test, so α = 0.25 could not have fired either. P3 therefore ran α = 0.6, 0.75 and 0.9 instead (`w3/queues/p3_pareto.txt`). N ∈ {24, 32, 40, 48} ran as planned. The selection rule of P3 was applied unchanged and gave α* = <!--n:select.alpha_star-->1.0<!--/n--> and N* = <!--n:select.n_star-->40<!--/n--> (`python3 -m w3.select_star`).
2. **tuned and noradix were not re-run in P4.** The report's tuned (N* = 40) and noradix bars are the single runs from P3 (`tuned_n40_r1`) and P2 (`noradix_r1`), n = 1 each.

Other differences:

- **The gate as built** (`patch/peak_kv_reservation.diff`) differs from the pseudocode in 3.2:
  - a running request subtracts its `cached_tokens` as the shared prefix. After prefill, `prefix_indices` covers the whole prompt (387 tokens, of which 36 are shared), so subtracting it would undercount what each running request frees at finish by almost a whole prompt and make the gate over-conservative;
  - finished requests are skipped, and the idle test is "no unfinished running request and nothing admitted this round";
  - the reserve is `max(IGNORE_EOS_RESERVE_TOKENS, page_size)` tokens per live request;
  - the gate is skipped for hybrid-SWA and dLLM models;
  - the scheduler passes α to `PrefillAdder` (`None` when the flag is off) instead of `add_one_req` reading the flag;
  - the log line `Peak-KV reservation delayed admission` is written at most once per 5 s, so the `#delays` it prints is a lower bound.

  [`patch/README.md`](../../patch/README.md) describes the final algorithm and a known inaccuracy in its docstring (note C3).
- **P1.** The upstream queue also ran a deterministic qps-0.2 run (`traces/reasoning_q0.2.jsonl`: the q2 prompts and lengths, slower arrivals, no retractions). It became the reference for the correctness checks.
